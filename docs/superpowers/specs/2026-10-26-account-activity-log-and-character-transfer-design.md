# 账号操作日志 + 后台角色转移（一人多号鉴别）设计

- 日期：2026-10-26
- 状态：待用户审阅
- 范围：Worker（Hono）+ MySQL 迁移 + Web 前端（`apps/web`）+ 一次性补数脚本

## 1. 背景与目的

有人用一批 QQ 邮箱注册了多个 ltsd 账号，然后来找管理员，要求把某个游戏角色从一个账号换绑到另一个账号。现有规则：角色被某账号绑定后 30 天内其他账号不能绑定（`KE_BINDING_EXCLUSIVE_MS`，`apps/worker/src/ke/service.ts` 的 bind 流程），满 30 天后其他账号再绑就自动转过去（`transferCharacter`）。来找管理员的人，实际是想跳过这 30 天。

目前管理员没有任何数据判断"这几个号是不是同一个人"：系统刻意不存明文 IP（限流只存 HMAC 摘要，KE 表只存 SHA-256 的 `ip_hash`/`ua_hash`），`auth_security_events` 里没有 IP。

本次要做两件事：

1. **记录**：在账号的关键操作上记录明文 IP、城市级地理位置、运营商、浏览器指纹、设备 ID、UA，形成一张统一的操作日志表，供日后鉴别一人多号。
2. **后台角色转移工具**：管理员输入源账号 A → 选 A 名下的角色 → 输入目标账号 B → 系统调出两个账号的全部操作记录做关联分析 → 展示结论、证据和并排时间线供人工审核 → 管理员填备注后确认转移。

将来会做"自助换绑"（本次不做），届时会复用本次的日志表和分析算法，所以数据越早开始积累越好。

## 2. 目标 / 非目标 / 反目标

**目标**

- 新增一张操作日志表，覆盖第 4.1 节列出的所有操作，每条带明文 IP + 城市 + 运营商 + 指纹 + 设备 ID。
- 管理员后台新增"角色转移"区块，按第 4.3 节的流程工作，分析报告按第 4.4 节的版式展示。
- 关联分析是**可解释的规则打分**：每条证据单独计分并展示，管理员能看到分数从哪来。
- 一次性补数脚本：把 KE 表里已有的 `ip_hash` 还原成明文 IPv4 并补上城市，写入日志表。
- 隐私政策页补充说明（第 4.6 节）。
- KE `start` 增加角色归属检查，堵住"角色转走后旧主仍能启动"的漏洞（第 4.7 节）。

**非目标**

- 不做同意弹窗，也不等隐私政策的 30 天通知期（用户决定直接上线）。

- 不做用户自助换绑（以后单独做）。
- 不做自动封号、不自动拦截注册、不自动拒绝转移——数据只当证据，判断由管理员人工做。
- 不接第三方 GeoIP API（实时数据用 Cloudflare 自带的 `request.cf`）。
- 不做 Turnstile、一次性邮箱拦截等注册风控（讨论过，本次不做）。
- KE 客户端（IWA，位于其他仓库）本次不改，KE 侧事件只有服务端能拿到的 IP/地理/UA，没有指纹和设备 ID。

**反目标（做了也算失败）**

- 记录日志导致注册、登录等主流程失败或明显变慢。
- 指纹/IP 证据被当成"定论"：网吧、宿舍、同型号手机会撞指纹和 IP，算法必须对公共 IP、常见指纹、机房 IP 降权，并在报告里写明。
- 分析报告只给一个分数、说不出理由。
- 转移后出现数据不一致：角色归 B，但配置、分享、运行中的实例还卡在 A 那边导致报错。

## 3. 约束

- 账号、KE 数据都在 MySQL（`migrations/mysql/`），新表也放 MySQL，迁移编号接在 `021_ke_standalone_modules.sql` 之后。
- 真实客户端 IP 统一取 `trustedAuthClientIp()`（`apps/worker/src/auth/rate-limit.ts`）：生产取 `cf-connecting-ip`，本地是 `localhost`，其他环境是 `unknown`。地理信息取 `request.cf`，测试和本地环境下可能不存在，字段允许为空。
- 管理员接口沿用 `apps/worker/src/admin/router.ts` 的 `guarded()`：非管理员一律 404；写操作要过会话 CSRF。
- 定时清理挂在现有 cron 上（`apps/worker/src/index.ts` 的 `scheduled`，`*/5` 那一档已经在跑 KE cleanup）。
- 生产库操作遵守 `agent.md` 的"有界查询"原则：查询必须走索引或有严格 LIMIT，补数脚本对生产库只做只读、有界查询，写入前由用户审阅生成的 SQL。
- 站点在欧盟（ltsd.ro），明文 IP 和指纹都算个人数据：必须有保留期，隐私政策要写明用途。

## 4. 已确定的方案

### 4.1 操作日志表

新表（暂名 `account_activity_log`），每条记录：

| 字段 | 说明 |
|---|---|
| `user_id` | 操作所属账号 |
| `event` | 操作类型（见下表） |
| `result` | `SUCCESS` / `FAILURE` |
| `ip` | 明文 IP（`unknown` 时存空） |
| `ip_net` | 匹配用的网段：IPv4 = 完整地址；IPv6 = `/64` 前缀。分析时按它比较"同一 IP"，并建索引 |
| `country` / `region` / `city` | 来自 `request.cf`（英文名，原样存） |
| `latitude` / `longitude` | 来自 `request.cf`，用于"异地并发"判断 |
| `asn` / `as_org` | 运营商编号与名称 |
| `is_hosting` | 是否机房/VPN IP（见下） |
| `device_id` | 浏览器本地存的设备 ID（仅网页端事件） |
| `fingerprint` | 浏览器指纹哈希（仅网页端事件） |
| `user_agent` | 原始 UA，截断到合理长度 |
| `ref` | 关联对象，例如 KE `instance_id` |
| `aid` / `cid` / `nid` | KE 绑定、启动、绑定失败等事件涉及的角色（其他事件为空）；`aid` 建索引 |
| `source` | `live`（实时记录）/ `backfill`（补数脚本写入） |
| `request_id` / `created_at` | 请求 ID、毫秒时间戳 |

需要的索引：`(user_id, created_at)`、`(ip_net, user_id)`、`(device_id, user_id)`、`(fingerprint, user_id)`、`(created_at)`（清理用）。

**记录哪些操作：**

| 操作 | 记录时机 |
|---|---|
| 注册 | 注册成功 |
| 点击邮件验证 | 验证成功（会同时发放免费权益，是最关键的一步） |
| 登录 | 成功；以及"账号存在但密码错误"的失败（不存在的邮箱不记，因为没有账号可挂） |
| 找回密码 | 申请（账号存在时）、确认重置成功 |
| 修改密码 | 成功 |
| KE 设备码批准 | 用户在网页上批准设备码时（网页端，带指纹） |
| KE 设备 token 发放 | KE 客户端换到 token 时（KE 端，只有 IP/地理/UA） |
| KE 实例绑定 / 启动 | bind、start 成功 |
| KE 绑定被拒 | bind 因"该角色 30 天内已被其他账号绑定"（`KE_CHARACTER_BOUND`）失败时，记在**尝试绑定的账号**名下，带上角色 `aid/cid/nid`。来找管理员换绑的人几乎都先用 B 试绑过，这条是"B 碰过这个角色"的直接证据。该错误在 bind 事务内抛出、事务会回滚，所以必须在事务外写日志 |
| KE 心跳 | 仅当本次 IP 与该实例上次记录的 IP 不同时记一条（避免心跳刷爆表） |
| 留言板发帖 / 回复 | 成功 |
| 后台角色转移 | 确认转移时，A、B 各记一条。**这两条不带任何网络字段**（IP、地理、指纹、设备 ID、UA 全空，因为请求来自管理员自己的浏览器），并且分析算法忽略这类事件，否则管理员的 IP/设备会把所有经手过的账号互相"关联"起来 |

**写入原则：** 尽力而为。日志写入失败只记错误日志（`logError`），不影响主流程的返回；不得为写日志给主流程加锁或拉长事务。

**地理信息：** 写入时直接从 `request.cf` 取 `country`、`region`、`city`、`latitude`、`longitude`、`asn`、`asOrganization`，存下来，以后不再回查。

**机房/VPN 判断：** 按 `as_org` 匹配一份常见云厂商/机房关键字清单（如 Alibaba、Tencent、Amazon、Google Cloud、Microsoft、DigitalOcean、Vultr、Linode/Akamai、OVH、Hetzner 等），命中即 `is_hosting = 1`。清单写成常量，后续可加。

**保留期：** 180 天，挂在现有 cron 的清理任务里分批删除（每批有上限）。

### 4.2 浏览器指纹与设备 ID

- **设备 ID**：网页端首次访问时生成一个随机 UUID 存进 `localStorage`，之后一直复用。清缓存或无痕模式会丢，这是已知局限。
- **指纹**：网页端用稳定的浏览器特征（屏幕尺寸与像素比、时区、语言、平台、CPU 核数、内存档位、canvas 绘制结果、WebGL 渲染器等）算一个哈希。自己实现轻量版本，不引入有授权限制的指纹库。
- 两者通过请求头随**会写日志的网页端请求**一起发给服务端（注册、登录、验证邮箱、找回/修改密码、批准设备码、留言板发帖等）。
- 服务端把它们当作**不可信输入**：只校验格式（长度、字符集），不合格就当作没带；不能因为没带或格式错就拒绝请求。

### 4.3 后台角色转移流程

放在现有管理员后台页面（`apps/web/src/admin-page.ts`）里，新增"角色转移"区块。

**第 1 步：选角色。** 输入源账号 A（邮箱或用户 ID）→ 点"查询角色" → 下拉框列出 A 名下当前绑定的全部角色（角色名、`aid`、等级）。

**第 2 步：填目标。** 输入目标账号 B（邮箱或用户 ID）→ 点"转移（先分析）"。

**第 3 步：分析报告**（定稿版式，见第 4.4 节的报告结构）：

1. 顶部：结论 + 关联分（如"高度疑似同一人　关联分 87 / 100"）。
2. 证据区，两栏：左栏"强证据"；右栏"弱证据"和"反向 / 降权"。每条证据前带编号 ①②③…
3. 两号并排时间线，直接展开（不折叠）：三列"时间 / 账号 A / 账号 B"，每行一条操作，显示操作类型、IP、城市、运营商、指纹短码。证据涉及的行高亮，并带上与证据相同的编号，方便对照。右上角有"只看高亮行"开关；日志多时分页或下拉加载。
4. 底部：审核备注输入框 + "确认转移"、"取消"按钮。

**第 4 步：确认转移。** 必须填备注。点"确认转移"后：

- 服务端**重新计算一次**分析结果（不信任前端传回的分数），和备注一起存进 `admin_audit_log.detail` 作为快照：结论、分数、证据列表（不存完整时间线）、被搬动的配置 ID、被断开关联的分享 ID。审计日志不随 180 天清理删除。
- 因为快照永久保存，**快照里不得出现完整 IP、指纹、设备 ID**：每条证据存结构化字段（规则 ID、加减分、次数/热度等计数）加一句脱敏后的说明（IP 只保留前两段，如 `113.87.x.x`；指纹/设备 ID 不出现）。完整信息只存在于 180 天的日志表里。页面上实时展示的报告可以显示完整 IP。
- 分数高低都允许确认，判断交给管理员。

**转移时数据怎么动（在一个事务里完成）：**

- `ke_characters`：`user_id` 改为 B，`bound_at` 设为当前时间（B 从此重新计 30 天锁定期，与自动换绑一致）。
- `ke_profiles`：A 名下该角色（`aid, cid, nid` 相同）的全部配置改归 B。若 B 名下该角色已有同名配置，搬过来的那份改名加后缀以避开唯一键；若 B 名下该角色已有激活中的配置，搬过来的全部设为非激活。
- `ke_shared_profiles`：A 已发布到配置大厅的分享**仍留在 A 名下**，并把这些分享的 `source_profile_id` 置空，断开与被搬走配置的关联。否则 B 以后保存该配置时，会因为"共享配置不属于当前账号"报 403（见 `publishSharedProfile`）。
- `ke_instances`：**不动**。实例仍归 A；A 正在运行的不打断（用户决定），但 A 之后无法再启动这个角色（见第 4.7 节）。
- 校验：确认时在事务内重新检查"角色此刻仍属于 A"；A、B 不能是同一个账号；B 必须是已验证邮箱的正常账号（`ACTIVE`）。任一不满足就失败并提示。
- A、B 的操作日志里各记一条"后台角色转移"。

### 4.4 关联分析算法

**输入：**

- A、B 两个账号在保留期内的全部操作日志（含补数记录），每个账号设读取上限（例如 2000 条），超出时在报告里注明。
- **未经身份验证的尝试不作为证据**：登录失败、申请找回密码只要知道邮箱就能以任意账号的名义产生，若计入打分，别人可以伪造两个账号的关联。这类记录只在时间线展示，不参与任何规则、不计入"有效记录数"，热度统计也不算它们。
- 两号出现过的游戏账号 `aid`：主要来自日志表的 `aid` 列（保留 180 天，含"绑定被拒"事件），再并上当前 `ke_instances` / `ke_characters` 里的值。注意 `ke_instances` 会被定时清理（IDLE 1 天、STOPPED/KICKED 7 天），`ke_characters` 只有当前归属，二者都只能当补充。
- 对两号共用的每个 IP 网段、指纹、设备 ID，额外做一次有界查询：保留期内有多少个**不同账号**用过它（"热度"）。

**规则打分**（权重写成常量，便于以后调；下面是初始值）：

| 类别 | 规则 | 分值 |
|---|---|---|
| 强 | 两号日志里出现同一设备 ID：热度 ≤ 2 个账号 +45；3–5 个账号 +15；> 5 个账号视为公共电脑（网吧等），0 分并注明 | 0 ~ +45 |
| 强 | 两号出现同一指纹：热度 ≤ 3 个账号 +30；4–10 个账号 +10；> 10 个账号视为常见指纹，0 分并注明 | 0 ~ +30 |
| 强 | 两号在 30 分钟内先后使用同一 IP 网段（多次只算一次，报告里写次数） | +25 |
| 强 | 被转移角色的 `aid` 也在 B 名下出现过 | +30 |
| 强 | 除被转移角色外，两号还共有其他 `aid` | +20 |
| 中 | 注册链：一个号的注册与另一个号的任一操作相隔 24 小时内，且同 IP 网段或同设备 | +15 |
| 中 | 共同 IP 网段（任意时间），每个 +8，上限 +24 | 0 ~ +24 |
| 弱 | 两号各自最常出现的城市相同 | +5 |
| 弱 | 两号最常用的运营商（ASN）相同 | +3 |
| 弱 | 出现完全相同的 UA 字符串 | +3 |
| 降权 | IP 网段热度 3–5 个账号：该 IP 相关加分 ×0.5；> 5 个账号：视为公共 IP（网吧、学校等），×0 并注明 | — |
| 降权 | 证据所在 IP 是机房/VPN（`is_hosting`）：该条加分 ×0.3 并注明 | — |
| 反向 | 两号在 10 分钟内分别出现在不同国家 | −20 |
| 反向 | 两号在 10 分钟内分别出现在相距较远的不同城市 | −10 |

- 总分截断到 0–100。
- 结论分档：≥ 70 "高度疑似同一人"；40–69 "可能是同一人"；< 40 "无明显关联"。
- **数据不足**：任一账号的日志少于 3 条时，结论直接显示"数据不足，无法判断"，分数灰显，只作参考。
- 每条规则产出一条证据，包含：类别（强 / 弱 / 反向）、一句人话说明、加减分、对应的时间线行。没命中的规则不显示。降权的情况以"反向 / 降权"证据形式展示，说明打了几折、为什么。
- 算法实现为**纯函数**（输入日志和热度数据，输出分数、结论和证据），不直接查库，便于单元测试。

### 4.5 一次性补数脚本

- 放在 `scripts/` 下，手动运行，不进 Worker。
- 从生产 MySQL **只读、有界地**读取：`ke_instances`（`user_id`、`aid`、`ip_hash`、`updated_at` / `last_heartbeat_at`）和 `ke_tokens`（`user_id`、`ip_hash`、`created_at`）。
- 把这些 `ip_hash`（未加盐的 SHA-256，原文是 IP 字符串）与整个 IPv4 空间逐一比对，还原出明文。还原不出来的（IPv6）跳过。
- 城市用离线库 DB-IP City Lite 查（免注册，英文地名，与 `request.cf` 的英文名风格接近）。
- 输出一个 SQL 文件，写入日志表：`source = 'backfill'`，`event` 标为对应的 KE 操作，`created_at` 用原记录的时间。由用户审阅后自己执行。重复执行不能产生重复记录（需要幂等）。
- 已知局限：每个实例只能补到最近一次的 IP，补不到注册时的 IP；没用过 KE 的账号补不到任何数据。另外 `ke_instances` 会被定时清理（IDLE 1 天、STOPPED/KICKED 7 天后删除），所以补数的主要来源实际是 `ke_tokens`（过期/撤销 7 天后才删），能补到的量可能不多。

### 4.6 隐私说明

**用户决定：随本次功能直接上线，同时更新隐私政策；不等 30 天通知期，不做同意弹窗。**

现有隐私政策页（`apps/web/src/privacy-page.ts`）是英文、按 GDPR 结构写的，按原有结构用英文补充：

- 数据类别：新增"安全与防滥用数据"——IP 地址、大致地理位置（城市级）与运营商、浏览器 UA、存放在浏览器本地存储中的随机设备 ID、浏览器指纹哈希；收集时机为注册、登录、邮箱验证、密码相关操作、KE 设备授权与绑定、留言板发帖。
- 用途与合法依据：防止滥用与欺诈、处理账号与游戏角色归属纠纷；合法依据为正当利益（Art. 6(1)(f)），写进现有的合法依据表格。
- 保留期表格：上述数据 180 天；角色转移审核结论（IP 已脱敏）随审计记录长期保存。
- Cookies 一节：说明设备 ID 存于本地存储，属于安全所必需。
- 更新 "Last updated" 日期。

### 4.7 KE 启动时的角色归属检查

现状：KE 的 `start`（`apps/worker/src/ke/service.ts`）只检查"实例属于当前账号、上报的角色与实例一致"，不检查角色现在归谁。所以角色转走后，A 对旧实例直接 `start` 仍能拿到授权。现有的 30 天自动换绑也有同样的漏洞。

改动：在 `start` 的事务里，校验完实例归属和角色一致之后，再查 `ke_characters`。如果该角色已归属**其他账号**（`user_id` 非空且不等于当前账号），就拒绝启动。

- **复用现有错误**，不新增错误码：与 bind 被拒完全相同——`KE_CHARACTER_BOUND`、HTTP 409、文案"该角色 30 天内已被其他账号绑定"、附带 `bound_at`。转移和自动换绑都会把 `bound_at` 设为当时，所以这句文案在这两种场景下都成立。
- `user_id` 为空（无主角色）时保持现有行为，不拦截。
- **心跳不加检查**（用户决定：正在运行的不用管）。
- 这条检查同样作用于 30 天自动换绑：B 绑定后，A 不能再启动该角色，与 bind 的行为一致。

## 5. 设计者代为决定的事项（请审阅时留意）

1. 登录失败只记录"账号存在但密码错误"，不存在的邮箱不记。
2. KE 心跳只在 IP 变化时记录。
3. 机房/VPN 用运营商名称关键字清单判断。
4. 指纹自研轻量版，不引入第三方指纹库；指纹和设备 ID 只做证据，不做拦截。
5. 日志保留 180 天；转移审核快照随审计日志永久保存。
6. IPv6 按 `/64` 前缀比较是否"同一 IP"。
7. 地名直接用 `request.cf` 返回的英文名，不翻译成中文；补数用 DB-IP City Lite 以保持英文风格一致。
8. 转移时配置跟着角色走，大厅分享留在 A 并断开关联；A 的实例不动（用户已确认"正在运行的不用管"）。
9. 目标账号 B 必须是已验证邮箱的正常账号。
10. 算法权重和分档按第 4.4 节的初始值，写成常量。
11. KE 客户端本次不改，KE 侧事件没有指纹和设备 ID。
12. KE 绑定因 30 天锁定被拒时也记一条日志（记在尝试绑定的账号名下），日志表单独存角色 `aid/cid/nid`。
13. 设备 ID 和指纹一样按"热度"降权，避免网吧公共电脑误判。
14. 永久保存的审计快照里 IP 脱敏到前两段，不含指纹和设备 ID。
15. "后台角色转移"日志不带网络字段，且不参与打分。
16. KE `start` 归属检查只拦"角色归属其他账号"，无主角色（`user_id` 为空）照旧放行。

## 7. 验收标准

- 第 4.1 节表中每种操作在成功（以及指定的失败）后都会写入一条日志，字段完整；日志写入失败时主流程照常返回。
- 生产环境下，日志里的城市、运营商来自 `request.cf`；本地和测试环境下这些字段为空，不报错。
- 超过 180 天的日志会被定时任务分批清理。
- 后台能按第 4.3 节完成"查角色 → 分析 → 审核 → 确认"全流程；非管理员访问相关接口得到 404；确认时不填备注会被拒绝。
- 转移后：角色归 B 且 `bound_at` 已更新；A 的该角色配置归 B，且无唯一键冲突；A 的大厅分享仍在、可访问，且与配置断开关联；A 正在运行的实例不受影响；审计日志里有分析快照（IP 已脱敏）和备注。
- KE `start`：角色已归属其他账号时返回 `KE_CHARACTER_BOUND`（409，文案与 bind 相同，带 `bound_at`）；角色归属自己或无主时行为不变；心跳行为不变。
- 隐私政策页已按第 4.6 节更新。
- 分析算法有单元测试，覆盖每条规则、各项降权、反向扣分、"数据不足"和分档边界。
- 补数脚本在本地用构造数据跑通：能还原 IPv4、跳过 IPv6、重复执行不产生重复记录。
- `pnpm lint`、`pnpm typecheck`、`pnpm test` 通过；涉及 MySQL 的改动有对应的集成测试。
